ENGO BUILD FIX - KEEP TWO-JOB PARALLEL BUILD
===========================================

What the two supplied logs actually show
----------------------------------------
1. Local PC: Python 3.13 was paired with Nuitka's downloaded MinGW64 compiler.
   Nuitka stopped with: "non-MSVC is not currently supported with Python 3.13".
   Fix: force MSVC with --msvc=latest.

2. GitHub Actions: the workflow already passed -NuitkaJobs 2. The GitHub log
   confirms "Logical processors: 2" and the builder confirms "--jobs=2".
   At 188m 6s, MSVC failed compiling module.google.genai.types.c (131,067th
   generated C line) with C1002: compiler is out of heap space in pass 2.
   The workflow then kept hanging on leftover compiler processes until the
   hosted-job cancellation at about 237 minutes. A PowerShell Runspace error
   appeared during cancellation because of the old Ctrl+C callback.

Important parallel-build decision
---------------------------------
- The normal GitHub workflow in THIS package explicitly uses --jobs=2.
- --low-memory is NOT enabled in the normal workflow. Nuitka documents that
  --low-memory implies --jobs=1, which would violate the requested 2-job build.
- The optional PowerShell switch -LowMemory is retained only as a manual
  emergency fallback if the two-job build still hits C1002. Use it only when
  choosing to trade parallelism for lower memory pressure.
- MSVC is forced with --msvc=latest; --lto=no remains enabled.
- Fatal MSVC/SCons errors are detected early so orphaned processes are stopped.
- The GitHub build timeout is 360 minutes and the cache key is updated for the
  MSVC two-job configuration.

What is and is not fixed
------------------------
- The local Python 3.13 / MinGW incompatibility is addressed by forcing MSVC.
- The GitHub workflow remains parallel on exactly two Nuitka compiler jobs.
- The timeout/cancellation handling is improved.
- The recorded GitHub C1002 is a genuine compiler-memory failure in the very
  large google.genai.types.c translation unit. Keeping two jobs does not prove
  that C1002 is eliminated; the new run will tell us whether the updated process
  handling and MSVC setup are enough. If C1002 repeats, the true memory-saving
  fallback is -LowMemory, which necessarily runs one compiler job, or a runner
  with more RAM. Do not claim that both --low-memory and --jobs=2 can be active.
